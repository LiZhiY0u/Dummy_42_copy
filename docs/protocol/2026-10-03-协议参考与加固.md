# 协议参考与 V1 第一轮加固

日期：2026-10-03。目标：在 STM32F103 内存预算内完善现有 Qt ↔ P9 串口协议，保持 V1 帧格式、命令编号和 revision=1 兼容。不自动使能、烧录或执行运动，不把研究建议写成已实现功能。

## 1. 官方项目参考

访问日期为 2026-10-03；latest/master 链接可能变化。本轮只借鉴设计原则，不复制源码，不引入依赖，也不移植整套通信栈。

| 项目 | 查到的机制 | 借鉴与限制 |
| --- | --- | --- |
| [ODrive Native Protocol](https://docs.odriverobotics.com/v/latest/manual/protocol.html) | endpoint 0 提供接口 JSON；其他端点请求携带接口定义 CRC；序号对应请求应答 | 借鉴真实接口描述、兼容性检查。文档明确服务端不按序号过滤重发，不能取代本项目的副作用命令去重；不在 F103 上立即引入动态 JSON 端点体系 |
| [MAVLink Command Protocol](https://mavlink.io/en/services/command.html) | 匹配的命令确认；长任务区分进度与最终结果；未确认时重传 | 借鉴确认/执行中/完成分层和有界恢复。本项目不自动重试运动/保存/校准，当前缓存与持久化不足以保证所有副作用重发安全 |
| [MAVLink 去重说明](https://mavlink.io/en/guide/redundancy_deduplication.html) | 讨论多链路重复命令；提出幂等操作和主通道策略 | UART/CAN 应有明确所有权；包序号不天然等于业务事务 ID，不把“有序号”当作全链路 exactly-once 保证 |
| [VESC packet.c](https://github.com/vedderb/bldc/blob/master/comm/packet.c) | 长度上限、CRC、有限接收缓冲、坏帧逐字节重新尝试解析 | 借鉴帧层/命令层分离、错误恢复与固定内存测试；不换成它的帧头/大小端/CRC布局，避免破坏现有兼容性 |

研究判断：继续现有 V1 更合适。当前主要缺口是能力描述失真、会话重连边界、构建追踪和运动后端未接入，而不是缺少另一种帧头。采用成熟协议可验证的语义，不重写已有帧层。

## 2. 已落地改动

### 能力声明与实现一致

P9 GET_INFO capabilities 从 `0x187` 改为 `0x180`，只置位清故障与遥测。位置/速度/电流模式虽可在固件选择，但对应目标命令未实现，不能宣称完整运动接口可用。现有 Qt 已按能力位拦截 ENABLE 和目标命令，因此不需要新增 UI 开关。

UID 使用已有 HAL_GetUIDw0/w1/w2 读取，再按小端显式序列化，保持原 12B 布局。硬件边界可以替换，电脑测试可真正执行 GET_INFO，而不解引用 MCU ROM 地址。

### 新会话有独立序号空间

原缓存及 pending 只按 SEQUENCE 筛选；HELLO 的 SESSION 始终为 0，新 token 的 SEQ1 会撞旧 HELLO。

修复后，普通请求按 SESSION 区分，完整 HELLO 按 PAYLOAD token 区分。同作用域同序号仍必须完全同内容，否则 SEQ_CONFLICT。不同 token 不被旧缓存误判，但仍经过运行状态及邮箱占用检查：运行时 WRONG_STATE，旧握手 pending 时 BUSY。不会清除故障或放宽使能条件。

这是软件层缓存碰撞修复，不宣称全部交错或快速重连已完成硬件验收。

### 握手确认丢失时有界恢复

主机 HELLO 首次 200ms 未确认，将相同 token、SEQUENCE、SESSION、PAYLOAD、CRC 的帧原样重发一次；第二个 200ms 仍无应答则报错，不无限重连、不换 token。

同 token HELLO 不清故障、不重置水位、不续期心跳。两次确认均丢失时，主机停止启动流程；设备没有有效心跳时仍按原 500ms 看门狗处理。原只读查询重试保留，运动、Flash 保存、校准不自动重试。

## 3. 验证证据

按失败用例 → 最小修复 → 完整回归的测试驱动流程执行。

| 用例 | 修复前 | 修复后 |
| --- | --- | --- |
| 已完成 HELLO 后新 token/SEQ1 接管 | 误判冲突，断言失败 | 通过；新会话成功，旧会话心跳拒绝 |
| 旧 HELLO pending 时新 token/SEQ1 | 未返回预期 BUSY，断言失败 | 通过；新请求 BUSY，旧请求成功完成 |
| 运行状态下新 token/SEQ1 | 未返回预期 WRONG_STATE，断言失败 | 通过；保留会话并拒绝接管 |
| GET_INFO 能力与目标命令一致 | 声明 0x187，断言失败 | 0x180；三个目标命令仍 UNSUPPORTED |
| 第一个 HELLO 确认丢失 | Qt 启动失败 | 相同帧重试一次后 Ready |
| 全部 HELLO 确认丢失 | 只发一次，不满足新约定 | 恰好两次相同帧，然后报错 |

Qt 完整软件套件：95 passed、0 failed、1 skipped；包含 14 项初始化/清理，跳过真实串口 opt-in 用例。日志：`build/host-p4/tests.log`。本次日志覆盖构建目录旧日志，早期实机摘要保留在独立验证文档。

P9 实际 uart_protocol.cpp 主机回归：原用例及 `cached-takeover`、`pending-takeover`、`running-takeover`、`info-capabilities` 均通过；原编码器 SPI、UART TX、UART echo 测试均通过。硬件替身测试不等于实机测试。

使用现有 ARMClang 6.7 编译变更 UART 单元（Cortex-M3、Thumb、-Oz、short enum/wchar、无 RTTI/异常），与既有正常模式对象重新链接并导出 HEX。Code=45432、RO=5016、RW=92、ZI=8540。出现既有 `MT6816_base.h` 大小写告警，本轮没有扩展修复。

当前正常候选栈：main=280B、receiver=88B、IRQ=344B、SysTick=0、预留=128B，估算 840B/1024B。此报告对应本次编译，不能混用旧对象的 1024B 估算；仍需高水位测量。本轮是增量编译/链接，不宣称全工程干净重建或实机压力验收。

独立只读审查未发现本轮新增 Critical/Important 问题；其范围是三处新行为，不是全协议认证。

本轮没有烧录、打开硬件串口、使能或转动电机，没有安装工具，没有提交/推送。旧诊断 HEX 备份未覆盖。

## 4. 后续路线

1. **P0 正常模式验收。** 实机复测 Ready/心跳/状态/遥测/STOP/重连；测编码器有效性、ISR 时间与栈高水位，补噪声/半帧/CRC/突发测试。不能仅凭编译或静态栈通过就开放运动。
2. **P1 兼容诊断扩展。** 考虑新增只读命令返回构建标识、运行配置、RX overflow、CRC error、TX response/telemetry drop、队列高水位，保持现有 INFO 50B/Snapshot 48B 不变。须明确计数器与更新上下文，定义老固件 UNKNOWN_CMD 回退，补独立测试向量。本轮未分配编号或实现该接口。
3. **P2 运动闭环。** 先完成一个模式的校验→边界执行→真实目标反馈→停止/失联退出，验收后才置相应能力位；测试电流/速度范围依据实际供电和机构确定。
4. **P3 任务与持久化。** 区分接受/规划完成/实际到位；保存区分接受/写入/读取校验；校准提供进度/取消/终态查询，事件丢失由查询恢复。明确 Flash 原子提交和掉电恢复，以及 UART/CAN 统一所有权。

改变既有字段布局或语义才考虑提升 revision；不要混淆线版本、参数 schema 与固件构建号。本轮修复实现以符合既有约定，revision 保持 1。
